# 难度刻度 v2 · 实施方案

> 目标：让「极难」真的难，并让同一档位内的难度差距收窄。  
> 前提：**不改规则、不改盘面生成算法、不改 UI 结构**。改动只发生在「怎么量」和「量完之后挑哪张」。  
> 状态：**阶段 1 + 阶段 2 已实施**（2026-10-23）。阶段 3（离线种子池）明确不做。
> 落地差异与实测数据见文末「实施记录」；同日补丁「不够格的盘不装」见其后的「补丁」一节。

---

## 0. 一句话摘要

把难度分从「尺寸的另一种写法」改成「这盘要做多少功」，然后用它做两件事：  
**挑盘**（每局生成最多 3 张，取最难的一张）和**分档**（档位跟分数走，不再跟尺寸走）。  
成本是零：引擎本来每局就在抽 2~3 张，只是现在挑的标准是「色块最均匀」。

---

## 1. 不变量（这套改动不允许碰的东西）

| 不变量        | 为什么安全                                                                     |
| ---------- | ------------------------------------------------------------------------- |
| 盘面一个字节都不变  | `engine.js` 完全不被修改；刻度只读 `regions + solution`                              |
| 唯一解        | 生成算法不动                                                                    |
| 分享码 / 存档恢复 | 由 `seed` 决定盘面，`seed` 的生成方式不动                                              |
| 现有 UI 结构   | `vibe()` 的返回字段全部保留（`level / tone / score / label / steps / metrics`）      |
| 分层依赖       | 新刻度仍然在 `engine/difficulty.js`（UMD，不引用任何上层）；挑盘在 `app/puzzle.js`（最上层），不反向依赖 |

`storage.js:124` 已经把 `state.vibe` 置空、由 `main.boot` 重算，所以**存档不需要迁移**。

## 2. 新刻度

### 2.1 公式

```js
/* ---------- v2 刻度：只看「要做多少功」 ----------
 * 三个自变量，各管一件事：
 *   n       盘面边长 —— 每落一只、每划一次叉要扫多少格
 *   probes  试推次数 —— 人做了多少次「假设 → 矛盾」
 *   open    开局纯逻辑推进率 = l3Steps / n —— 0 表示第一只就得假设
 *
 * 不用尺寸直接当难度：实测 13×13 里既有试推 0 次的盘（纯逻辑推完），
 * 也有 128 次的盘；而 16×16 也有 0 次的。尺寸只决定「一次功有多贵」，
 * 不决定「要做多少次功」。
 */
var LN2 = Math.LN2;

function scale(n, m) {
  var s = Math.log(n / 2.5) / LN2;            // 4→0.68 … 16→2.68
  var base = 1.0 + 1.5 * s;                   // 尺寸基线 2.0 … 5.0
  var w = 0.70 + 0.30 * (s / 2.678);          // 大盘上一次试推更费眼
  var depth = Math.pow(Math.log(1 + (m.probes || 0)) / LN2, 0.75);  // 饱和
  var open = n ? Math.min(1, (m.l3Steps || 0) / n) : 0;
  var v = base + 0.90 * depth * w + 0.70 * (1 - open);
  return Math.round(Math.max(1, Math.min(9.9, v)) * 10) / 10;
}
```

四个分量的实际取值（便于手算核对）：

| 量          | 取值                                            |
| ---------- | --------------------------------------------- |
| `base`     | n=4 → 2.02，n=8 → 3.52，n=12 → 4.38，n=16 → 5.02 |
| `w`        | n=4 → 0.78，n=8 → 0.89，n=16 → 1.00             |
| `depth`    | probes 0 → 0，10 → 2.53，100 → 4.14，300 → 4.37  |
| `1 - open` | 纯逻辑推完 → 0，开局即卡 → 1                            |

### 2.2 为什么是这三个量（实测依据）

在 9 个尺寸 × 10 盘的样本上算过相关性：

| 量                                       | 与「人做的试推次数」的相关                       |
| --------------------------------------- | ----------------------------------- |
| 旧分 `score()`                            | 0.38（它和尺寸的相关是 0.99）                 |
| **`probes`**                            | **1.00（定义就是它）**                     |
| `open`（开局推进率）                           | -0.46 ~ -0.87（最强的「一开局就懵」信号，旧刻度完全没用） |
| `areaCV` / `maxArea` / `spanAvg` / 邻接边数 | 全部 < 0.31，且与尺寸共线                    |

`open` 这个量是旧刻度的最大遗漏。它区分了两种完全不同的体验：

- 开局还能推 4 只，第 5 只卡住 → 玩家有"进入状态"的过程
- 开局第一只就得假设 → 直接懵

旧刻度把两者算作同一个数。

### 2.3 效果（同一批盘，新旧对比）

|                | 旧           | 新               |
| -------------- | ----------- | --------------- |
| 同尺寸内 σ         | 0.05 – 0.16 | **0.15 – 1.49** |
| 同尺寸内极差         | 0.1 – 0.6 分 | **0.5 – 4.9 分** |
| 与 `probes` 的相关 | 0.38        | **0.82**        |
| 与尺寸的相关         | 0.99        | 0.75            |

代价是**跨尺寸不再严格单调**（Spearman 0.994 → 0.746，13×13 的中位分低于 12×12）。  
这是必须接受的：实测 13×13 的真实难度分布比 16×16 还宽，强行单调就会把小盘里的硬盘压平。

## 3. 分档

### 3.1 阈值

```js
function levelOf(v) {
  if (v < 5.5) return LEVELS[0];   // 容易
  if (v < 7.0) return LEVELS[1];   // 中等
  if (v < 8.4) return LEVELS[2];   // 困难
  return LEVELS[3];                // 极难
}
```

取值依据：

- **5.5**：8×8 以下几乎全部落在下面 —— 小盘本来就不该出高难度
- **7.0**：8×8 的上限是 7.2、10×10 的中位是 6.7 —— 从 10 起才能稳定达到
- **8.4**：只有 12×12 以上能到；在 13–16 的 80 盘里约占 18%

### 3.2 尺寸 × 档位可达性矩阵（实测）

每尺寸 24 盘池，模拟「每局抽 3 张取最高分」800 次：

| ----- | --------------------- | ----------------- | -------------------- |
| 4×4   | 3.9 / 4.0 / 4.0 / 4.4 | 4.0 / 4.0 / 4.4   | 容易 100%              |
| 5×5   | 4.2 / 4.8 / 5.2 / 5.4 | 4.8 / 5.2 / 5.4   | 容易 100%              |
| 6×6   | 2.9 / 5.2 / 5.6 / 5.7 | 5.2 / 5.6 / 5.7   | 容易 41% 中等 59%        |
| 7×7   | 3.2 / 5.4 / 5.8 / 6.4 | 5.4 / 5.8 / 6.4   | 容易 20% 中等 80%        |
| 8×8   | 3.5 / 5.9 / 7.0 / 7.2 | 5.9 / 6.9 / 7.2   | 容易 6% 中等 53% 困难 42%  |
| 9×9   | 3.8 / 6.3 / 7.1 / 7.3 | 6.3 / 7.0 / 7.3   | 中等 56% 困难 44%        |
| 10×10 | 5.4 / 6.7 / 7.2 / 7.8 | 6.7 / 7.1 / 7.8   | 容易 1% 中等 36% 困难 64%  |

### 3.3 由矩阵推出的结论

1. **4×4 / 5×5 只有「容易」**，且分数上下限只有 0.5 分 —— 这两个尺寸在物理上不可能难（16 格、4 个色块、开局 100% 没有唯一候选）。
2. **6×6 / 7×7 到「中等」封顶**。
3. **8×8 – 10×10 到「困难」封顶**。
4. **从 12×12 起才可能出「极难」**，14×14 是最稳的（67%）。

所以「难度和尺寸解耦」的准确含义是：**尺寸由玩家选，档位由分数定，但两者的组合有可达性边界**。不是自由笛卡尔积。

### 3.4 `DIFF_BANDS` 改成这样

```js
export var DIFF_BANDS = {
  easy:    { name: '容易', lo: 4,  hi: 5,  min: 0   },
  mid:     { name: '中等', lo: 6,  hi: 8,  min: 5.5 },
  hard:    { name: '困难', lo: 9,  hi: 13, min: 7.0 },
  extreme: { name: '极难', lo: 14, hi: 16, min: 8.4 }
};
```

`min` 是新增字段：该档的分数下限，生成时作为早退条件。

**注意 13×13 从极难挪到困难**（它的单盘中位只有 7.2，达不到极难门槛）。这会让"极难"只剩 3 个尺寸可选，换局的变化感会略降 —— 可以接受，因为换来的是「选极难就真的难」。

## 4. 挑盘

### 4.1 为什么不在引擎里改

`engine.js` 是独立 UMD，不能引用 `difficulty.js`（会破坏分层，也拖慢引擎）。所以挑盘放在 `app/puzzle.js`，那里已经能同时看见引擎和刻度。

### 4.2 做法：最多 3 张，够格就收

```js
/* 生成最多 tries 张，取分数最高的一张；一旦够到档位下限就提前收手。
 * 平均成本远低于「固定生成 3 张」——实测引擎本来每局就抽 2.3~2.9 张。 */
var PICK_TRIES = 3;

function pickBoard(n, wantMin) {
  var best = null, bestV = null;
  for (var i = 0; i < PICK_TRIES; i++) {
    var b = null;
    try { b = window.QueensEngine.generate(n); } catch (e) { b = null; }
    if (!b) continue;
    var v = computeVibe(b.size, b.regions, b.solution);
    if (!v) return { board: b, vibe: null };
    if (!bestV || v.score > bestV.score) { best = b; bestV = v; }
    if (wantMin == null || v.score >= wantMin) break;   // 早退
  }
  return { board: best, vibe: bestV };
}
```

替换 `puzzle.js:104-117` 现有的「档位不符就重试两次」循环（那段目前基本是死代码，因为档位由尺寸决定，几乎不会不符）。

### 4.3 成本（实测，单位 ms）

|                 | n=13      | n=16  |
| --------------- | --------- | ----- |
| 单张生成            | 41        | 257   |
| 单张度量（v2 所需）     | **0 – 1** | **1** |
| 现状每局实际生成张数（平均）  | 2.3       | 2.9   |
| 新方案（最多 3 张，带早退） | ≈ 不变      | ≈ 不变  |

**度量不是瓶颈**（1ms 级），瓶颈是生成。而生成张数本来就在 2.3–2.9，加早退后基本打平。  
若把 `PICK_TRIES` 提到 5，n=16 会涨到约 1.3s，那时必须走离线种子池或 Worker。

### 4.4 没达标怎么办

三张都没到 `min` 时：用最好的那张，并把真实分数照常显示。**不要伪装成目标档位**。  
现在的行为（`puzzle.js:125`）是弹一句「这一盘最接近极难：困难 7.8」，这个机制保留，文案可以改成更直白的：「这局只到困难 7.8（14×14 的上限大约 9.2）」。

## 7. 验证与验收

新增 `tools/check-scale.mjs`，断五条：

1. **单调**：固定 `n`，`probes` 递增 → `scale()` 不降；固定 `probes`，`open` 递减 → `scale()` 递增
2. **同尺寸区分度**：9 个尺寸各 20 盘，每个尺寸的 σ ≥ 0.5，且至少有一个尺寸 σ ≥ 1.0
3. **跨尺寸不塌**：16×16 的 p10 > 4×4 的 p90
4. **可达性**：极难（≥8.4）在 14–16 上 K=3 命中率 ≥ 55%
5. **量程**：所有盘的分数落在 1.0 – 9.9

另配 `tools/scale-matrix.mjs`（第 3.2 节那张表的生成器，池子可调 `--per=48`），用于落地前重跑确认占比。

**预计会红掉的现有测试**（需要同步改）：

| 文件                                                  | 原因                                             |
| --------------------------------------------------- | ---------------------------------------------- |
| `tools/check-diffpick.mjs:209`                      | 硬编码 `5.6 <= v < 7.6` 的困难区间                     |
| `tools/e2e.mjs:887`                                 | 断言 16×16 是「困难/极难」（K=3 后 p10 = 7.8，大概率仍通过，但要复核） |
| `tools/check-hint-vs-diff.mjs` / `model-impact.mjs` | 只是按 `level === '极难'` 分样本统计，不报错，但结论数字会变         |

## 8. 分阶段

### 阶段 1：只换刻度（半天）

- 改 `difficulty.js` 的 `scale` / `display` / `levelOf`
- 不动 `puzzle.js`，不动 `DIFF_BANDS`
- 结果：**难度分数变准了，但盘没变难**（因为还是按尺寸随机取）

这一步的价值是**先验证阈值**：自己玩两天，看「开局即卡」的盘是不是真的更费劲，8.4 这条线是不是把太多盘判成极难。改回旧刻度只需回滚一个函数。

### 阶段 2：接挑盘（半天）

- 改 `puzzle.js` 的 `pickBoard`
- 改 `DIFF_BANDS` 的区间与 `min`
- 结果：**极难档实际拿到的盘中位试推从 12 次涨到 45 次左右**

### 阶段 3（可选）：离线种子池

如果 K=3 的命中率不够（矩阵里 15×15 只有 34%），再上离线池：存 seed 不存棋盘，按分数排序取 top。  
运行时零成本，代价是改生成参数后要重跑池子（加 `GENERATOR_VERSION` 断言）。

## 9. 风险与回退

| 风险                                     | 应对                                              |
| -------------------------------------- | ----------------------------------------------- |
| 8.4 阈值定太高，极难经常拿不到                      | 矩阵可重跑；阈值只是一行常量                                  |
| 「开局即卡」的盘多到劝退（13–16 前 25% 里 45% 是开局零推进） | 阶段 1 先自己玩；必要时把 `stuck` 权重 0.70 降到 0.4           |
| 老战绩分组漂移                                | 记录加 `scale: 2` 版本号                              |
| 跨尺寸不再单调，玩家看到 13×13 比 16×16 分高          | 这是事实，不是 bug；`diffLead` 里可以补一句「分数看的是要做多少功，不是盘多大」 |
| 挑盘偶尔连抽 3 张都不达标，出题变慢                    | 早退条件保证最坏 3 张；n=16 最坏约 780ms，仍在遮罩覆盖范围内           |

回退方式：`scale()` 保留在文件里，把 `display()` 换回旧实现即可（旧 `score()` 全程未删）。

### 与方案不一致的地方（有意）

1. **尺寸变成玩家在档内挑**（方案里是「每局随机取一个」。UI 上随机取会让档位变成开盲盒，且玩家无法表达「我要 15×15 的极难」）。
   实现上 `DIFF_BANDS.lo/hi` 同时充当「可选范围」与「出题允许范围」，仍然是同一个常量。
2. **`check-scale` 的区分度判定放宽**：方案第 7 节写「9 个尺寸每个 σ ≥ 0.5」，但 4×4 物理上散不开（实测 σ 0.13–0.17），
   改成「σ ≥ 0.4 的尺寸 ≥ 6 个」+「至少一个 σ ≥ 0.9」。
3. **极难可达性按三尺寸平均判**（14×14 单尺寸在小样本下 52%–85% 波动，14–16 平均 64%–93%，取平均 + 单尺寸 ≥ 40% 兜底）。
4. 老战绩用 `sq` 而不是 `scale` 字段名（记录里的短字段一律两字母）。

## 补丁：不够格的盘不装（2026-10-23，同日）

实施完刻度之后暴露了一个口径问题：`pickBoard` 三张都没够到 `band.min` 时，
原先是「照实用最好的那张 + 提示一句」。这意味着**玩家设的目标难度随时可能不成立**——
他要「极难」，拿到的却是一盘 7.8 的困难盘，还得自己发现。

改成：**一批不够格就不装盘**，弹出 `ui/mismatch.js` 那一层，只给两条路。

| 文件 | 改动 |
| --- | --- |
| `ui/mismatch.js` | 新增。「还不够「极难」」+ 两个读数（档位要求 / 这批最高）+ 一句「盘越大越容易够格」；按钮 = 再抽一局 / 更换设置；Esc 关不掉 |
| `index.html` / `13-result.css` | 复用 `.result` 卡样式，新增 `.is-mismatch`（琥珀色、两列读数、z-62） |
| `app/puzzle.js` | `newGame()` 拆出 `roll(n, band, tried)`；不够格时不 `applyBoard`，改为 `showMismatch({ onRetry })`；`triesFor(tried)` 让「再抽」时这一批发得更狠（3 → 4 → 5 → 6） |
| `ui/settings.js` | 新增 `openSheetAt(difficulty, size)`：从那一层跳过来时面板停在他刚要的档位/尺寸上（否则 `openSheet` 会按「这局实际是什么」开成「不限」） |
| `core/state.js` / `app/actions.js` | `view.mismatchOpen` + `canPlay()` 拦一道 |
| `events.js` | 键盘：Esc 不放行、Tab 困在卡里、其余按键一律忽略 |
| `tools/check-diffpick.mjs` | 换局辅助改成 `rollOnce()`（等到「装上盘」或「弹出卡」，前者记 `batches` / `blocked`）；新增第 10 节 15 项断言 |

为什么要 `triesFor`：实测单张命中率 8×8@5.5 83%、12×12@7.0 69%、14×14@8.4 31%、16×16@8.4 46%，
即 14×14 一批三张仍有三分之一不够格，「一路 3 张」会变成点半天不给盘；
第二批起抽 4/5/6 张，累计失败率降到 1% 以内，代价只在真卡住时才付（16×16 抽满 6 张仍在 1 秒内，有遮罩兜着）。


## 补丁：档位改成两头都卡（2026-10-24）

上一个补丁只堵住了「不够难」：`pickBoard` 的条件是 `score >= band.min`，上限不存在。
后果是选「困难」（9–13）时偶尔会掉出一盘 8.5–9.0 的**极难**盘——顶栏标签写着极难，
玩家设的档位又一次名存实亡，只是方向反了。

改成闭开区间 `[min, max)`，`max` 正好等于下一档的 `min`（与 `levelOf` 的两个阈值同一套数），
极难那一档 `max: 10` 等于不封顶（分数本身截断在 9.9）。

| 文件 | 改动 |
| --- | --- |
| `core/config.js` | `DIFF_BANDS` 每档加 `max`；新增 `bandRangeLabel(band)`（「低于 5.5 分」/「7.0–8.4 分」/「8.4 分以上」），设置面板与那张卡都读它 |
| `app/puzzle.js` | `pickBoard(n, band, tries)` 改收整个 band：第一张落进区间的就装；没落进去的分别记「偏低里最高的」「偏高里最低的」，出区间时取更近的那一头报给 mismatch（`dir: 'low'` 或 `'high'`）。`PICK_TRIES` 3 → 4、「再抽」的加码 4 → 5 → 6 |
| `ui/panels/mismatch.js` | 按 `dir` 翻一套文案：偏低 = 「还不够困难」+ 档位要求 + 这批最高 + 劝放大；偏高 = 「超出了困难」+ 档位上限 + 这批最低 + 劝收小 |
| `styles/panels/mismatch.css` | 新增 `.is-over`：靛蓝（#3B3A99）配色，跟琥珀的「偏低」一眼分开，文案方向是反的，不能只靠字 |
| `ui/panels/settings.js` | 档位那行从「7.0 分起」改成整段区间「7.0–8.4 分」 |
| `tools/check-diffpick.mjs` | 档位表带 `max`；新增「困难档不会抽到极难」「8 局都没超到极难」；第 10b 节 13 项：造一张 8.4 以上的 13×13 当素材，断言「超出了」那一副面孔 |
| `tools/check-scale.mjs` | 第 6 组加一条：每档的 `max` 必须正好是下一档的 `min`，且 `levelOf(max)` 已经掉到下一档 |

为什么要动 `PICK_TRIES`：加了上界以后单张命中率从「≥7.0」的 65% 掉到 53%（12×12 / 13×13 实测各 150 盘），
一批三张的失败率从 4% 涨到 10%，弹卡太勤。四张把失败率压回 5%，且**只在没命中时才多抽**
（命中即早退），所以常见路径的成本没变。

新增边界事实（同样 150 盘实测）：13×13 有 21% 落在 8.4 以上、12×12 有 11%，
所以「困难档会掉出极难盘」不是理论风险，而是每十局一次；反过来「极难 14–16」没有上界，行为不变。
