Queens Puzzle · Difficulty Study

这个局面到底有多难？
——难度量化、尺寸上限与加难可行性

测量对象：engine.js 出题引擎 + index.html 呈现层 · 共采样 130 张 4–16 棋盘、17–26 共 12 张超界盘、4 组对照变体
本报告只做验证，未修改游戏任何文件。

三句话结论

  1. 能量化，而且可以验证「量得对」：难度可以拆成 5 层推理技巧 + 4 个结构量，分数随尺寸严格单调（Spearman 0.995），推理层零误伤。
  2. 16 之后能跑但不好用：出题耗时按 n6.7 爆炸（n=24 已 1.7 秒、n=25 近 10 秒），最大色块涨到均面积的 5–10 倍，n≥18 出现相邻同色，手机端 n>22 直接溢出。
  3. 「加难度」目前只有尺寸一个真旋钮：面积再均衡、挑种子都试过，分数分别 −1 分和 +2 分；因为 95% 的盘本来就必须假设试推——难度上限被「缺少逻辑入口」这件事锁死了。

1能不能用数字指标量化一局的难度？

能。但先要承认一件事：「电脑解得快」不等于「人解得难」。这个题型（Star Battle 单星变体）的人类技巧链是清楚的，我按技巧谱系建了 5 个档位，再用一个不带任何搜索的传播器去跑，看它卡在哪一档。

1.1 度量模型：5 个技巧档 + 4 个结构量

档名称玩家实际在做的事判定方式
1直觉型某色块/行/列只剩一个空格，直接落子只开「唯一候选」规则就能解完
2封锁型某色块全挤在一行里 → 这一行别处全排除+ k=1 的区块封锁
3计数型3 个色块只能落在 3 行里 → 这 3 行被它们占满+ k≤3 的集合计数（列同理）
4试推型「假如放这儿…立刻矛盾，划掉」，反复假设+ 单层失败文字探测（failed literal）
5试错型真猜，猜错回退重来以上都推不完，必须回溯搜索

  sizeBase = log(n/3.2) / log(16/3.2)    // 尺寸基线
  shape    = ½·min(1, areaCV/0.55) + ½·min(1, (areaMax/n)/2.6)  // 色块畸变
  gift     = 1 − min(1, 单格色块数 / 0.25n)  // 白送的已知子
  logic    = 档1→0.06 / 档2→0.22 / 档3→0.42 / 档4→0.60 / 档5→0.76+0.05·猜测深度

权重不是拍脑袋定的：sizeBase 用对数是因为玩家感受到的负担更像「一眼要扫多少格」，而不是格数的平方；logic 给 36% 是因为档位一跳，人就要换一套思维方式。

上面这套 0–100 是「研究分」，只用来做统计和排序（数值压在 43–83 之间，说白了主要是尺寸计）。游戏界面里显示的是另算的 1–10 体感分：以尺寸为基线（4×4 ≈ 1.8，16×16 ≈ 9.2，对数插值），再用推理深度做 ±0.6 修正，最后分成 容易 / 中等 / 困难 / 极难 四档。两者同源，但后者才是给玩家看的刻度。

1.2 先验证「量得对不对」：三道关

104盘唯一性被独立复核（13 尺寸 × 8 盘），异常 0 盘
0 / 0推理层误划 / 错子（共 392 个色块 × 3 档 + 试推层）
0.995Spearman(均分, 尺寸)，13 个尺寸全部单调
  • 唯一性复核：另写了一个完全不使用位掩码的参考求解器（tools/refsolve.mjs）重数解，逐盘比对解向量。n=16 时最坏搜索节点 1757，说明「唯一解」这个前提是真的，不是引擎自说自话。
  • 推理层无误伤：这是最容易出错的地方——推理器一旦「划掉」本该放皇后的格子，整盘就废了。逐盘检查：凡是推理器落下的子，必须与真解一致；凡是没解完的色块，真解所在格必须还活着。三个档位全部 0 违例。
  • 单调性：均分 43（n=4）→ 83（n=16），中间的每一级都比上一级高，没有回头。

1.3 再说「量得有多细」：同尺寸内其实没什么可分辨的

这是本报告最需要如实交代的一段。分数随尺寸非常准，但把尺寸固定住之后，分数能提供的信息很有限：同尺寸标准差只有 1.0–7.8 分（13 个尺寸平均 2.9 分），8 盘里的极差通常 3–8 分。

n=14 那 7.8 分标准差来自一张「恰好有单格色块」的盘（档 1，58 分），是唯一一次难度明显偏低的情况——单格色块等于白送一只皇后，后面整条推理链会连锁点亮。

换成秩相关看，同尺寸内分数与各项指标的关系是：

所以第 1 题的答案是：能量化，但要分两层用。
  • 绝对难度（跨尺寸比较）→ 现在的分数够用，误差约 ±3 分，排序可靠。
  • 相对难度（同尺寸比两张盘）→ 别用 0–100 的分数，直接用 guessDepth（要猜几层）和 probes（要假设多少次）这两个原始量更诚实。分数在同尺寸内的分辨力只有 ρ≈0.5。

1.4 一个意外的发现：95% 的盘根本没有「逻辑入口」

130 张盘（4–16 各 10 张）的技巧档分布。档 4 = 必须做「假设→矛盾」，档 5 = 必须真猜。

把 130 张盘全跑一遍：档 1 只有 1 张、档 2 只有 1 张、档 3 有 7 张、档 4 有 121 张（93%）。也就是说，93% 的局面在「唯一候选 + 区块封锁 + 集合计数」这套纯逻辑里一步都推不动——不是玩家不会推，是盘面上真的没有可推的东西。

原因在生成算法：每只皇后先占住自己色块的种子格，再让色块往外长，长成细长锯齿状（scoreOf 里 diff − 1.5·same 的偏好），并且允许单个色块长到 2.4n 格。结果是每个色块都横跨 3–5 行、3–5 列，既不会「全挤在一行里」也不会「几个色块共用几行」，计数推理的触发条件永远不成立。真正能当入口的只有一种：面积恰好为 1 的色块（白送一只皇后）。

这解释了一个直觉上的怪现象：4×4 和 16×16 在玩家体感上都「一开始不知道从哪下手」，只是 16×16 要假设的次数更多（平局猜测深度 1 → 3.7 层）。

2能不能继续扩大棋盘？超过 16×16 是什么表现？

技术上能，我实测到 26×26 都还能出唯一解。但四个层面会依次撞墙，而且撞的顺序很明确：先是出题耗时，然后是色块畸变，然后是配色和布局，最后是 32 位掩码。

为什么会这么陡？因为 buildRegions 每染一格就要解一次盘验唯一性，落子次数是 n²−n（n=24 时 552 次），每次求解的上限是 12 万节点。棋盘一大，「唯一解」这件事本身变难证明，求解器更容易吃满预算、判为失败，于是回溯变多，耗时就滚起来了。拟合出来的指数是 6.72，外推 n=32 约 13 秒——而这个数字还是单线程阻塞主进程的耗时，界面上就是「点了一下，页面对着动画开始卡住」。

2.2 色块会「长残」：巨块吞掉半个盘

最大色块面积 ÷ 平均面积（= n）。1.0 表示所有色块等大，5 表示最大块是平均的 5 倍。

n=13 起这条线从 2.1 跳到 3.0 以上，n=26 直接到 10。原因还是同一个：生成时只看「唯一解」，面积上限 maxAllowed = 2.4n 只在收尾时用来「够用就收工」，rebalance 的预算又只有 40 次检查。棋盘越大，一次长歪的色块越难被拉回来，最后就出现「一个色块占 263 格、剩下 25 个色块挤在角落」的极端局面——玩家看到的不是推理题，而是一张几乎没分块的棋盘。

2.4 算法天花板的真实位置：n = 32

求解器和推理层都用 rowMask |= (1 << r) 这样的 32 位整数掩码，每行/列/色块占一位。JS 的移位按 32 取模，所以：

1 << 31 = -2147483648   (1<<31) & 1 = 0   // 安全：符号位也能正常当标记用
1 << 32 = 1              (1<<32) & 1 = 1   // 第 33 行撞上第 1 行

实测反例：构造一个「每个色块 = 一整行」的棋盘（必然有多解），用参考求解器与引擎分别数解——

n参考求解器（无掩码）引擎 solve()判定
322 解2 解一致
332 解0 解（预算耗尽）结论错误

所以 n ≤ 32 是位宽安全区，n ≥ 33 求解器会给出错误结论（实践中表现为「永远证明不了唯一解」，于是出题一直失败）。不过这个墙远在布局和耗时的墙之后，属于理论边界，不是现实瓶颈。

第 2 题的答案：
  • 桌面/平板：n=18–20 可用（耗时 <0.5s，格子 37–58px），代价是偶尔出现巨块和同色相邻，需要同时改配色表与面积上限。
  • 手机：n=16 已经是舒适上限，18 勉强，20 起单格 <20px 且 iPhone SE 会溢出。
  • 不加架构改动：16 就是天花板。要往上走得先做三件事——异步出题（换 Worker，避免主线程冻结）、扩配色（≥n 色或改用图案/边框区分）、给 rebalance 加足预算压住巨块。

3增加棋盘难度的可行性

我在临时副本里试了三种旋钮（未改动 engine.js），同尺寸、同种子对比。结论先说：只有尺寸是真旋钮，其余两个都是噪声级。

  • 面积再均衡（A/B）不涨分数：最大色块从 2.79 压到 1.91，观感确实更整齐，但分数 81→79。副作用倒是明确：n=14 的试推步数从 63 涨到 140，出题耗时翻近 4 倍（33→123ms）。它改变的是「结构是否好看」，不是「档位」。

  • 尺寸是唯一强旋钮：n 每 +1，均分约 +3.5（4→16 是 43→83），而且提升是单调、稳定、不需要改算法的。

3.2 为什么其余旋钮无效：难度上限被「没有入口」锁死

回到 1.4 的发现：93% 的盘在纯逻辑层面推不动第一步。这意味着所有盘都被顶到「档 4」这个平台上，而档位只有 5 个，一旦大家挤在同一档，分数就只能在 shape（结构噪声）里浮动——这也解释了为什么 areaMax 与分数的相关系数高达 0.93，却依然调不动难度：它和 n 一起涨，属于共线，不是因果。

换句话说：想让难度真的上升，必须让盘面出现「更深的推理需求」，而不是让色块变瘦或变大。这需要改的是生成目标，不是后处理参数。

3.4 一个容易被忽略的事实：难度≠耐玩

现在的盘面有 93% 需要「假设→矛盾」才能推进，这对新手已经不友好；再往上加难度，边际收益很低，因为玩家真正的卡点会从「推理不够」变成「盘面太大、眼睛跟不上」。相比之下，把档位分布拉开（比如一半盘能在「封锁型/计数型」解决，一半需要试推）比整体抬高难度更能留住人。

另外提醒一句：UI 里的「自动标记 / 冲突提示 / 强制落子」三个开关会显著改变实际难度。forced 打开时等于把「唯一候选」这一步白送，也就是把档 1、档 2 的工作量抹掉。所以记录难度时应该和辅助开关一起记，否则同一张盘在两种设置下的体感完全不同。
