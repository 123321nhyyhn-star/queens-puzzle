Queens Puzzle · Hint Feasibility

能不能让提示「讲人话」？
——人类式逻辑提示的可行性分析

涉及文件：engine.js、difficulty.js、index.html · 采样 130 张 4–16 真实棋盘（每尺寸 10 盘）· 本报告只做分析，未修改任何游戏文件

三句话结论

  1. 可行，而且是「接线」不是「造轮子」：能讲人话的推理器其实已经写好了（difficulty.js 里的 propagate()），X 标记、唯一位置高亮这些 UI 也都在。缺的是「一步一解说」的出口，和一个方向的对偶规则。
  2. 你举的那条规则确实是缺的，而且它是对的：现有计数只做了「几个色块被几条线包住 → 划掉线上其它色块」，你举的是它的对偶「几条线只由几个色块包住 → 划掉这些色块在线外的格子」。实测 8% 的盘有整行单色；补上它，16×16 上平均提示条数 11.8 → 14.8、能多定 1.4 只皇后。
  3. 但必须接受一个前提：这批棋盘只有 6.9%（130 盘里 9 盘）能纯逻辑走完，其余 93% 一定中途卡住。所以提示必须带第四级「假设→矛盾」，否则大多数局按两下就没话说了 —— 好消息是 81% 的卡点都能讲成干净的二选一。

1现在这个「解题器」到底是什么

先纠正一个容易混的直觉：engine.js 里的 solve() 不是「推理器」，它是一个靠回溯数解的搜索器。它回答的是「这盘是不是唯一解」，不是「下一步该干嘛」。

1.1 它的原理：以「色块」为变量做深度优先搜索

把每个色块当成一个变量，取值 = 这只皇后落在色块里的哪一格。搜索时每一步挑候选最少的色块（MRV），用行/列位掩码判重，再跟已放的皇后做八邻接检查：

// engine.js · makeSolver(n) 内部（约 84–146 行）
function dfs(depth) {
  if (aborted || count >= limit) return;              // limit=2：数到 2 个解就够判「不唯一」
  for (每个未用的色块) {
    候选 = 该色块里 未被行/列占用、且不与已放皇后八邻接 的格子
    挑 候选最少 的那个色块               // MRV
  }
  for (cand of 候选) { 放下 → dfs → 撤回 }
}
  • 出题时：每给一格染色就立刻 solve(region, 2)，必须 count === 1 才保留这次染色（buildRegions，约 204–235 行）。一张盘通常要几百次求解调用，预算上限 9000 次。
  • 验码时：分享码载入后 validate() 也用它复核唯一解。
  • 它的输出：{ count, aborted, nodes }。没有「哪一步、为什么」，也没有「这条推理用了什么技巧」——它天生讲不出人话。

1.2 「提示」按钮其实在剧透，没有在推理

useHint()（index.html 约 2197 行）从头到尾没碰过求解器，它直接读游戏开局就存下来的 state.solution：

// index.html · useHint()
for (r = 0; r < n; r++) {
  i = r * n + solution[r];            // 直接抄答案
  if (marks[i] !== 2) { target = i; break; }
}
placeQueen(target);                    // 从上往下补第一只没放的

所以现在按「提示」，得到的是答案，不是思路；而且顺序是按行扫，不是按「此刻最容易想通的那一步」。这也是为什么这个按钮一旦按下去，乐趣基本就没了。

1.3 唯一像人的那段逻辑，藏在难度模块里

difficulty.js 才是真正的人类推理器：propagate()（约 115–227 行）维护一张「活格表」，反复做三件事 ——

记号规则玩家心里那句话代码位置
S1某色块 / 行 / 列只剩一个活格「这只皇后只能放这儿了」propagate 内 S1 段
Ak 个色块的活格只在 k 条线上 → 这些线上别的色块全划掉「这 3 块把 3 行占满了，别的进不来」applyCounting（188 行）
Bk 条线的活格只属于 k 个色块 → 这些色块在线外的格子全划掉「这一行整行都是这个颜色，那它就在这一行」没有
P假设某格有皇后 → 推到矛盾 → 划掉这格「假如放这儿……第 5 行就没地方了」solveByProbe（293 行）

但这段代码只被 analyze() 用来给难度打分（跑一遍看「能推到第几档」），从来没被 UI 用过，也不记录中间过程——它只返回「推了几步、是否解完」，不返回「这一步是谁、划掉了哪几格」。而 applyCounting 的搜索方向是从色块出发找行/列，没有从行/列出发找色块的那一半。

2一条「人类提示」到底需要什么

不是「给出一个正确结论」，而是「给出一个能自己验证的结论」。所以每一步必须包含三件东西：前提（看哪几格/哪几条线）、结论（落子，或划掉哪几格）、一句话（为什么）。规则谱系里每一级都能凑齐这三件，只是难度递增。

2.1 你举的例子，形式化之后是什么

前提 第 1 行的全部 n 个格子都属于同一个色块 G。
推理 第 1 行必须有一只皇后，它能站的位置都属于 G，所以这只皇后就是 G 的皇后 —— 也就是说，G 的皇后被锁在第 1 行。
结论 G 在第 2、3、4 行的其余 8 个格子，全部划掉。

这条规则在数学上不是「小技巧」，而是霍尔条件（Hall's condition）的另一个方向。现有代码里的 A 规则是「k 个色块挤进 k 条线 → 这 k 条线被它们占满」；你的是「k 条线只由 k 个色块覆盖 → 这 k 个色块被锁在这 k 条线里」。两者是同一条计数不等式的两侧，A 实现了一半，B 完全没实现。你举的整行单色，就是 B 在 k=1、线=行 时的特例。

3.5 卡住的时候，能不能讲清「假设」

纯逻辑卡住时，看「候选最少的色块还剩几个格子」：

2.0–2.2n≥7 时卡点处「候选最少的色块」还剩几格，几乎都是 2
81%的卡点（121 盘里 98 盘）可以直接讲成「这两个格二选一」
3.1–3.4只有 n=4/5 时卡在 3 个以上候选，二分讲不干净

这意味着「假设→矛盾」这种提示不是勉强的兜底，而是可以写成一句人话的正式技巧：

L4 话术示例 「色块 6 现在只剩两个位置：第 3 行第 2 列、或第 4 行第 6 列。先试第一个 —— 如果皇后在这儿，第 3 行第 4 列和第 4 行第 1、2 列就都被封住，色块 2 会一个位置都不剩，矛盾。所以只能是第二个。」

4推荐方案：新增一个 hint.js，三个老文件基本不动

核心判断：推理引擎是现成的，缺的是「状态输入」和「步骤输出」。所以方案的重点不是写算法，而是把 difficulty.js 里那套「活格表 + 传播」重构成一个可以「一步步问」的模块，并把它接到现有 UI 上。

4.1 接口草案

// hint.js（新增文件，浏览器/Node 双用，与 engine.js 同风格）
var H = QueensHint.forBoard(n, regions);

H.fromMarks(marks)        // 0=空 1=玩家× 2=皇后 → 初始状态
H.checkMarks(marks, sol)  // 体检：玩家标记里有没有「标反了」的
H.nextStep()                // 返回「一步」，见下
H.apply(step)               // 把这一步的效果落进状态（落子 / 划格）

// nextStep() 的返回：够 UI 直接渲染，不需要再算
{
  rule: 'single' | 'count-region' | 'count-line' | 'assume',
  level: 1..4,                  // 对应难度档
  place: 37 | null,              // 要落的子（S1 才有）
  kill: [3, 5, 12, ...],        // 要划掉的格（只含「现在还空着」的格）
  units: { regions: [5], rows: [0], cols: [] },   // 前提涉及的单位，用于高亮
  text: '第 1 行整行都是色块 3 …'            // 一句话
}

「nextStep() 只给一步」是刻意的：一次给一步，玩家点一下想一下，才有提示的节奏；同时它让「提示」和「答案」彻底分开。

4.2 关键设计：玩家的标记怎么进场（以及为什么要先「体检」）

有两种做法，推荐第二种：

做法优点代价
① 空盘预演
开局就把整条逻辑链算好存起来，提示按顺序播		完全独立于玩家操作，永远正确提示会和玩家当前棋盘「对不上」（比如建议填一个已经填掉的色块）
② 从玩家标记出发
把 marks 变成初始状态，实时推一步		跟着玩家走，指哪打哪；而且能顺手指出标错的格子必须先确认玩家标记没标反，否则结论会跑偏

好消息是「体检」几乎不花钱，因为唯一解有一个很强的性质：除了那 n 个解格，棋盘上每一格都本来就不该有皇后。所以玩家标的 × 里，只有标在 n 个解格上的才是错的 —— 检查只需 O(n²) 的逐格比对，而且能精确报出「第 4 行第 2 列这个 × 是错的」。同理，玩家放的皇后如果不在解上，也能直接指出来。

体检的三个出口
  1. 有错标 → 提示改为「这一步标反了」，高亮那一格（这可能是所有提示里最有用的一个）。
  2. 标记都合法 → 放心从当前状态推理，结论一定成立（所有前提都为真 ⇒ 推理出的结论为真）。
  3. 标记合法但推不出 → 走 L4 假设，或直接给答案。

4.3 五级提示阶梯

级技巧UI 形态实测可用性
L1唯一候选（色块/行/列）格子闪琥珀环 + 落子已有 computeForced，扩到行/列即可
L2A：色块 → 线高亮那几个色块 + 划掉的格子变半透明 ×已实现（applyCounting）
L3B：线 → 色块（你说的那条）高亮整行/整列 + 该色块其它格变 ×需新写（约 40 行）
L4假设 → 矛盾高亮 2 个候选 + 「试试这个」已实现（solveByProbe），81% 的卡点是二选一
L5直接给答案沿用现在的 useHint()已有，建议降级为「长按/二次确认」

选步策略建议按「最像人」排序，而不是「最强」：L1 优先 → L2/L3 取涉及单位最少的 → L4 只在前面都没有时才用；并且优先挑「玩家还没标过的格子」，避免提示总是重复已经做过的事。

4.5 明确不做什么

  • 不把逻辑闭包接到「自动打叉」上。computeAuto() 现在只做「皇后同行/同列/同邻/同块」的直接排除，这是玩家的安全感来源；一旦让它跑完整推理，等于替玩家解题，难度会塌。
  • 不在 render() 里实时跑推理。虽然只要 0.1–0.3ms，但 render() 在拖动涂抹时每帧都调；按「marks 变化的快照」缓存一步结果即可。
  • 不做「全自动播放解法」。提示的价值在节奏，不在效率。

?直接回答你的两个问题

① 现在的解题器是什么原理？

是以「色块」为变量、MRV 选支、行/列位掩码判重、逐个皇后做八邻接检查的回溯搜索器，唯一目的是数解（数到 2 个就停，用来判唯一）。它不产生任何「理由」，所以没法直接用来做提示。游戏里那个「提示」按钮根本没调它，而是直接读开局存下的答案；真正像人的推理器在 difficulty.js 里，但只被用来算难度分，而且少了你说的那一半规则。

② 能否实现人类思路的逻辑提示？那个「整行只有一个颜色」的例子对不对？

例子完全正确，而且它正是现有实现缺的那一半：现在的计数只做「色块 → 线」，你说的是「线 → 色块」，两者是同一个霍尔条件的对偶。补上它大概 40 行，代价极小，16×16 上能多给 3 条提示、多定 1.4 只皇后。

但光有规则不够：这批棋盘 93% 无法纯逻辑解完（difficulty.js 里 121/130 盘判为「试推型」）。所以真正可落地的形态是四级阶梯 —— 唯一候选 → 封锁 → 对偶封锁 → 假设矛盾，最后才是给答案；数据支持这个设计：中局 98% 以上有逻辑可讲，81% 的卡点能讲成干净的二选一。结论：可行，工作量中等，主要难点不在算法，而在「一次只讲一步」的话术与交互。
